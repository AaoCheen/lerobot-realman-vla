## 2. 目前建议：保留原件，按版本选择训练样本

- 研究同学的最近方案，可以先看 **95条 `realman_all`**，但要理解额外位置估计特征及下面的统计问题。
- 如果想研究纯图像＋机器人状态的7维输入，可从47＋52条源数据选取；不要为了删掉10维特征而覆盖现有数据。
- 不要把SO100的50条直接混入RM65，关节、维度、图像键名均不同。
- 不要直接使用老诊断报告中的坏集编号；`episode_index` 和 `file_index` 在不同版本中已经变化。

**95条 `realman_all` 已经不包含这4条对应的状态/动作轨迹**：47＋(52−4)＝95，本次逐帧前缀匹配验证通过。不要对95条再按旧episode编号重复删一次。

### 47条版本：episode1的图像时间对齐需优先复核

`realman_new` 的 **episode1 / file-003**：状态/动作524帧，但元数据两路视频段均为0～24.0333秒（721帧），腕部视频文件头也显示721帧；数据时间戳只有0～17.4333秒。

这是**已确认的长度不一致**，不等于视频损坏。需要定位状态应匹配视频的哪524帧，而不是盲目截掉末尾。修复前建议先不纳入训练。`realman_all` 中episode1的数值来源也对应此条，其视频长度检查虽通过，图像内容与状态是否对齐仍需回看，不能据此认为问题已经修好。

### 95条版本：全局统计正确，逐episode统计有残留

- `meta/info.json` 和真实 `state` 是10维，`meta/stats.json` 的state统计也是10维、count=46236；本次重算其state最小值、最大值、均值，完全匹配。
- 但是95条 `meta/episodes` 的 `stats/observation.state/min` 仍只有7维，**82条**的state统计count也与当前轨迹长度不同，符合追加特征和截尾后未同步逐episode统计的情况。

## 3. 这次实际检查了什么

- 全部5个数据集：`info.json`、tasks、episode元数据及全部状态/动作Parquet；轨迹数和帧数均与info相符。
- 检查状态/动作形状、有限值、夹爪范围、全零关节、frame_index、全局index、视频引用、元数据时间范围；上述严重数值/索引问题未检出，视频范围例外见episode1。
- 1042个MP4的ffprobe流头全部可读取；尺寸与引用检查通过，不等于全部帧都能解码，也不证明任务成功。
- 4个RM65版本中每条轨迹的非末帧 `action[t]=state[t+1,:7]` 完全一致；当前夹爪动作标签是下一帧反馈，不是另存的命令。
- 当前原始5条HDF5可读取，平均约30Hz、时间戳单调，最长相邻采样间隔约47.8ms，未检出qpos非有限值；没有将数GB原图全部展开到内存。
- 发现13组跨版本完整状态/动作数组相同的轨迹；更进一步，95条全可匹配到47＋48条源数据前缀。这只验证数值血缘，不把视频内容当作相同。

没有逐条人工判断物体是否真正抓起/放入盒子、遮挡、相机是否移动；没有校验所有图像内容与关节的时间同步；没有启动真机、训练或调用带删除选项的脚本。

## 4. 下一步按这个顺序做

1. 先研究采集记录和 `action[t]=qpos[t+1]` 的定义，再回看这4条候选及episode1两路视频。
2. 选定一个输入方案：7维纯机器人状态，或10维含插头位置特征；训练与现场输入保持一致。
3. 以源轨迹为单位划分训练/验证；95条及其47/52条原版属于同源数据，不能跨集合制造验证泄漏。
4. 用episode白名单或明确过滤规则选样，训练前重新计算统计。若以后需要物理删除，必须同时处理meta、Parquet及视频共享关系，**不要手工直接删MP4**。

结论：**本次没有删数据。52条源版本的4条是明确优先复核/排除候选，95条派生版已经排除它们；另有1条对齐问题及统计元数据需要处理。不是“把所有旧报告标坏的文件删掉就能开训”。**
