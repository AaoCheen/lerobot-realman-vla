# 03：训练中怎样看效果，为什么要跑这么久

## 1. 先区分“正常更新”和“任务做得好”

现在日志能回答前者，不能独自回答后者。

| 证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| step持续增加 | 优化器在更新 | 真机成功率提高 |
| loss有限、梯度有限 | 该批数值没有NaN/Inf | 没有过拟合 |
| 平滑后的训练loss下降 | 在训练分布上更符合流场监督 | 没见过的物体位置也能抓 |
| checkpoint完整 | 保存流程完成 | 模型必然能正确部署 |
| 固定条件下验证loss下降 | 留出示范上的流场拟合更好 | 接触、闭环误差累积后的任务一定成功 |
| 一致条件下真机成功率 | 对指定任务的直接证据 | 其他任务/场景也有同样表现 |

本次前20步`0.143→0.107`，后续run02曾记录step3500 loss约`0.0295`，说明训练目标在部分batch上降低；**这些是单批值，不是完整验证曲线，不能拿几个点就认定模型已经学会。**

## 2. loss到底怎么读

loss是归一化动作空间中，预测流场与`噪声-干净动作`的均方误差，不是角度误差，也不是“错误率”。`loss=0.03`不意味着97%成功。

本次全局batch只有8，而且样本、噪声、噪声时间都在变化，因此相邻记录上下波动很正常。看最近几十个记录的移动平均，比盯某一条更有意义。不同动作归一化统计、不同噪声采样配置下，loss也不宜直接横比。

日志里的`grad_norm`是裁剪操作返回的**裁剪前范数**。配置阈值1.0，所以首步显示2.6并不说明没有裁剪。非常大的突增、长期不有限、loss持续暴涨才需要优先排查。

`gpu_peak_gib`是rank0的PyTorch峰值分配统计，不是所有卡总显存，也不是nvidia-smi看到的进程完整占用。

## 3. 当前还缺少哪一层评估

32条验证episode已经留出，没有用于训练或状态/动作统计。**当前自定义训练循环没有创建验证DataLoader，也没有计算验证loss；`eval_freq=0`。** 保留验证集不等于已经有验证结果。当前也不自动执行真机或仿真成功率评估。

建议分三层做，先不打断正在运行的训练：

1. **训练健康度**：持续看step、有限loss/梯度、检查点保存成功。现有日志已经支持。
2. **检查点离线验证**：单独加载导出模型，对固定验证起点计算flow matching loss。固定或多次采样同一组噪声/时间，逐关节报告，确保各检查点可比。再采样真实动作块，反归一化后看关节误差、夹爪时序与动作连续性。当前需要另写评估程序，尚未实现。
3. **真机验证**：同学用一致的场景、初始物体位置分布、控制频率和成功定义，比较原基座、已有微调、当前检查点；记录成功数/总次数、失败类型和视频。不能只展示一次成功。先核对单位和动作范围，再低速限幅测试。

离线动作误差也有局限：同一图像可能有多种合理动作，某条预测与示范不同不一定错；反过来，逐帧误差小也不能保证多步接触任务成功。

当前只保留最新完整检查点。如果要比较5000、10000等阶段，须在后续保存替换前把该阶段的`pretrained_model/`另存或传给同学。**不必复制几十GB的training_state来做推理。** 本笔记没有改动自动保留策略，也没有额外复制模型。

## 4. 54075步从哪里来，为什么大约两天

这不是π0.5的硬性要求，而是当前准备脚本的预算：

```text
训练完整动作块起点 = 144194
全局batch           = 4卡 × 每卡2 = 8
计划轮数            = 3
总optimizer步数     = ceil(144194/8) × 3 = 54075
```

每一步都要对图像、任务/状态和整块50步动作做前向、反向与参数更新。模型内部处理32维动作和多个token，不是对7个数做一个很小的回归。

按约3秒/步：`54075×3≈162225秒≈45小时`。另外还有视频数据等待、初始化、检查点I/O。日志`seconds`从取到batch后开始计时，包含该步模型训练，不包含取下一批的等待和检查点保存，所以估算应以持续运行的墙钟时间为准。

耗时的具体来源包括：

- 全参数微调：视觉/语言/动作网络都需要梯度。
- Gradient checkpointing：用反向时重算来换显存。
- FSDP：多卡切分能装下模型，但细粒度包裹涉及大量参数通信。
- 两路视频解码、预处理和数据读盘。
- 保存FP32训练分片、优化器状态和BF16推理模型。

目前没有做逐算子或通信profile，不能断言哪一项是最大瓶颈，也不能把4卡与单卡速度简单按4倍换算。

## 5. 学习率调高能加速吗

**不会直接降低单步耗时。** 学习率是参数每次更新走多远，步数是计划更新多少次：

```text
总耗时 ≈ optimizer步数 × 平均每步墙钟时间 + 保存等开销
```

| 改什么 | 对耗时的直接影响 | 对效果的影响 |
|---|---|---|
| 提高学习率 | 同样步数通常仍花差不多时间 | 可能更快拟合，也可能发散或破坏预训练能力；不保证能少训 |
| 减少总步数 | 直接减少训练时长 | 可能欠拟合，也可能避免不必要的过拟合；需要验证依据 |
| 增大全局batch | 固定轮数时步数减少，但单步更重 | 改变优化行为、显存和吞吐，不能不测就认定更快 |
| 减少动作块长度 | 可能减小计算 | 改变任务时间范围与模型设定，不能只当速度开关 |
| 只训部分层或LoRA | 可降低部分训练开销 | 改变实验问题，不再是当前全参数微调对比 |
| 减少推理积分步数 | 加快部署采样 | 当前训练forward并不跑10次积分，对现有训练速度基本无帮助 |

当前学习率先用500步warmup升到约`1e-5`，再余弦衰减到`1e-6`。前几步lr非常小是预定warmup，不是卡住。

不要因为预计两天就直接提高学习率。**更有根据的做法是先评估5000步检查点，再决定是否值得跑完54075步。** 3轮不保证比1轮更好，低质量或高度重复的数据尤其需要验证。

## 6. 本次运行中改配置的边界

正在运行的Python进程已经读入配置；此时修改YAML不会让它自动调整学习率或总步数。当前resume还会恢复原保存配置和scheduler，不能靠改模板静默变更实验。

想缩短实验、修改batch或学习率时，要先明确是“另开一个新实验”还是“修改现有训练计划”，再调整配置和恢复逻辑。这里先把原理解释清楚，不修改当前任务、不启动额外GPU作业。

查看当前run02：

```bash
tail -f outputs/pi05_full_run02/metrics.jsonl
```

`tail`可以随时Ctrl+C退出；这是查看命令，不是训练进程所在终端。实际运行名以你设置的`PI05_OUTPUT_DIR`为准。
