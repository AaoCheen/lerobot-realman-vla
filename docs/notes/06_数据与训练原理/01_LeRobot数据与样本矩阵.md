# 01：LeRobot格式的数据，怎样变成训练矩阵

## 1. LeRobot是框架，LeRobotDataset是数据约定

LeRobot提供数据读写、策略、处理器和训练工具。`lerobot-realman-vla`把RealMan硬件采集与部署接到这套工具上。因此“用了这个仓库”和“用了LeRobot”可以同时成立。

本次读取的是`data/datasets/realman_merged`，`meta/info.json`标明`codebase_version=v3.0`。这里的v3是**数据格式版本**；Python包版本是**lerobot==0.4.3**，两个版本号不要混用。

磁盘分成三部分：

```text
data/datasets/realman_merged/
├── meta/
│   ├── info.json            # FPS、字段名、维度、文件定位模板
│   ├── stats.json           # 原数据统计；本次训练另算训练集专属统计
│   ├── tasks.parquet        # task_index → 任务文字
│   └── episodes/...         # episode长度、表/视频定位等元信息
├── data/chunk-000/file-000.parquet
│                           # 本地该文件包含178362行数值数据
└── videos/
    ├── observation.images.camera_global/...mp4
    └── observation.images.camera_left/...mp4
```

**Parquet是列式表，MP4存图像，元信息负责对齐。** 不能假定一个Parquet对应一条episode，也不能只复制Parquet而忽略视频。LeRobot v3可将多条episode合并到文件，用元信息定位。

## 2. 先看一条episode，不考虑神经网络

一条episode是一次连续采集轨迹，长度为`T`帧。数据标称30 FPS，因此第`r`帧约对应`r/30`秒。用`r`表示真实采集时间索引，后文用`τ`表示flow matching噪声时间，二者不同。

状态矩阵：

```text
S ∈ R^(T×7)

          J1     J2     J3     J4     J5     J6     gripper
第0帧   [ ...    ...    ...    ...    ...    ...      ... ]
第1帧   [ ...    ...    ...    ...    ...    ...      ... ]
 ...
第T-1帧 [ ...    ...    ...    ...    ...    ...      ... ]
```

这里前6列是**关节绝对角度，单位度**，第7列夹爪是归一化开合量，约0闭、1开。`observation.ee_pose`另有6列末端位姿，**当前π0.5配置不使用这个字段作为输入**。

动作表`A∈R^(T×7)`具有相同列顺序。本数据的定义是：

```text
A[r] = S[r+1]        r < T-1
A[T-1] = S[T-1]      最后一行重复最后状态
```

这是采集/转换代码的定义，也已对数值数据核对。它记录**下一帧实际测得的状态**作为动作监督，不是直接记录遥操作器发出的命令，不是`S[r+1]-S[r]`，也不是速度或力矩。

例如，本次实际Parquet的episode 0前两行，保留部分小数：

| 行 | observation.state | action |
|---|---|---|
| 0 | `[74.190,24.244,101.771,-1.321,49.750,-17.108,0.999]` | `[74.189,24.242,101.771,-1.322,49.750,-17.108,0.999]` |
| 1 | `[74.189,24.242,101.771,-1.322,49.750,-17.108,0.999]` | `[74.190,24.244,101.771,-1.323,49.750,-17.108,0.999]` |

可见第0行动作等于第1行状态。预测这些数以后，还需要部署程序把目标位置转换成厂商SDK命令，数据格式本身不负责驱动电机。

两路图像可以概念上写成：

```text
I_global ∈ R^(T×480×640×3)
I_left   ∈ R^(T×480×640×3)
```

它们实际压缩在视频中，取样时才解码，不会将整个视频矩阵一次放进GPU。

逐帧表还保存`timestamp`、`frame_index`、`episode_index`、`index`、`task_index`。本地任务表只有一条文字：`pick up the plug and place it in the box`。

**所以这份数据直接监督的是一个7维机械臂的抓取放盒任务。它没有仅凭“有三只机械臂”就自动变成三臂协同或折盒训练数据。** 三臂联合动作、折盒技能需要相应的观测、动作定义和示范。

## 3. 一行数据，怎样变成一个训练样本

配置`n_obs_steps=1`、`chunk_size=50`。抽中episode中的起点`r`后，输入只取该时刻：

```text
条件 C_r = 当前global图像、当前left图像、S[r]、任务文字

监督 Y_r = [ A[r]   ]
           [ A[r+1] ]
           [  ...   ]     ∈ R^(50×7)
           [ A[r+49]]
```

因此它学习的是`C_r → 未来一段动作分布`。不是把50张未来图像也交给模型；未来动作只作为训练标签，在部署时未知。

因为`A[r]=S[r+1]`，上面的动作块相当于未来状态目标`S[r+1]…S[r+50]`；但在episode末尾最后一行动作采用重复状态，不能无限延伸这个等式。

动作块长度50，对应标称约`50/30≈1.67秒`的命令序列。真实执行速度还取决于部署控制频率。

配置的`action_delta_indices=0…49`由LeRobot数据工厂换成`0/30…49/30`秒，从同一episode取标签。训练入口另外筛掉最后49个起点：

```text
允许 r + 50 ≤ T
每条episode可用起点数 = max(T-49, 0)
```

这是为了让50行标签都实际存在，避免越界补齐被当作真实动作参与loss。**没有删除原始轨迹文件或最后49帧。** 最后49帧仍可出现在前面起点的未来动作块中。

相邻样本大量重叠。例如`Y_r`和`Y_(r+1)`有49行动作来自相同时间段，不能将起点数等同于独立实验次数。

## 4. batch轴从哪里来

DataLoader随机抽取多个起点，它们可以来自不同episode、不同时间，不要求连续。

每张卡`B=2`时：

| 数据 | 每卡形状 | 轴含义 |
|---|---|---|
| global图像 | `[2,3,480,640]` | 样本、RGB、高、宽 |
| left图像 | `[2,3,480,640]` | 同上 |
| 状态 | `[2,7]` | 样本、关节/夹爪 |
| 动作标签 | `[2,50,7]` | 样本、未来时刻、动作维 |
| task | 长度2的字符串列表 | 每个样本的任务文字 |

图像解码成float张量后是CHW顺序、范围约`[0,1]`；与元信息中存储的HWC形状要区分。

四张卡合起来全局`B=8`。可以想象成一个`[8,50,7]`标签大张量分到4张卡，但代码并不需要把这个大张量集中到一张卡。

## 5. 本次筛选和训练轮次

```text
326条episode
  ├── 5条隔离候选（没有删除，不等于已确认失败）
  ├── 289条训练：158355帧 → 144194个完整动作块起点
  └── 32条验证：与训练episode互斥
```

归一化统计只用训练episode重新计算，避免验证信息泄漏。原`meta/info.json`的`train:0:326`只是原数据集的默认划分，本实验以`run_config/data_selection.json`记录的episode划分为准。

步数计划：

```text
一轮更新数 ≈ ceil(144194 / 8) = 18025
计划3轮   = 18025 × 3 = 54075次optimizer更新
```

DataLoader的`drop_last`和分布式补齐可能让每轮实际覆盖略有差别，所以这是预算近似，不是保证每个起点恰好出现3次。3轮是初始设置，不是π0.5规定必须训练的次数。
